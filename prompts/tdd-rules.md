## Template

```markdown
# TDD Rules

Updated: {{today's date}}

Use TDD. Tests verify behavior, not implementation, so they don't need to change when internals change.

1. **Red-green-refactor.** Write a failing test first. Write the minimum code to make it pass. Refactor with tests green. No production code without a failing test driving it.

2. **Don't mock internals.** Let {{the project's real internal services — e.g. "Postgres and Redis"; if the project has none, write "internal modules and collaborators"}} run for real. Mock only outbound calls to the public internet (third-party APIs, payment providers, etc.).

3. **Test through public interfaces only.** Never call or assert on private methods, internal state, or implementation details. To cover an internal branch, design an input/output case that exercises it through a public method.

4. **Inject non-determinism.** Clock, random, UUID/ID generation, and anything else time- or entropy-dependent must be injected as dependencies. Freeze the clock and seed randomness in tests. Never rely on {{the stack's now() equivalent}} or unseeded random inside code under test.

5. **Each test is isolated.** Start from a known clean state: {{the isolation mechanism actually in use — e.g. "transactional rollback per test, flushed Redis namespace"}}. Tests must pass in random order. If order matters, there's hidden coupling — fix it.

6. **Contract-test the things you do mock.** For every mocked external API, run a periodic contract test against the real service (or a vendor-provided sandbox). Stale mocks that drift from reality are worse than no mocks.

7. **One behavior per test.** The test name describes the behavior in plain language: `{{a realistic name in this project's naming style}}`, not `test_service_3`. If the name needs "and", split the test.

8. **No logic in tests.** No conditionals, loops, or computed expected values inside a test body. Use {{the stack's parametrized/table-driven idiom}} for variation. A test should read top-to-bottom as arrange → act → assert.

9. **Factories produce minimal valid entities by default.** Each test overrides only the fields relevant to the behavior under test. If most tests set many fields, the defaults are wrong.

10. **100% coverage — branches, not just lines.** Cover error paths, boundaries, and equivalence classes, not only happy paths. No coverage pragmas, no excluded files, no skipped tests to hit the number. If a branch is unreachable, delete it rather than ignore it. Measured with `{{the project's coverage command}}`. Coverage proves a branch ran, not that its outcome is pinned — see rule 13.

11. **Code and tests are self-documenting.** Names carry the meaning. No docstrings, no comments. If you want to comment, rename or extract until the code explains itself. Only exception: explaining *why* something non-obvious is done (a workaround, a deviation).

12. **Don't test deleted code.** When you remove a behavior, delete the test that drove its removal — never leave an assertion referencing a symbol the code no longer has. Every test must trace to live code a reader can find; the red→green that justified the deletion is a development step, not an artifact to keep. If behavior remains after the removal, assert that remaining positive behavior instead.

13. **Tests are an executable specification — the suite must be enough to rebuild the unit.** If all production code were deleted, a competent dev reading only the tests should be able to reconstruct behavior that is observably identical (the *contract*, not the internals — rule 3). This is stricter than rule 10: branch coverage proves every branch *ran*, not that its outcome is *pinned*. Assert the exact observable result — the returned value, the persisted row, the emitted event, the error code and message — never merely that something is truthy, non-empty, or "was called"; an assertion a plausible-but-wrong implementation could still satisfy specifies nothing. Choose domain-meaningful inputs and outputs so the reader infers the *rule*, not a magic number: `charges_20_percent_late_fee_after_grace_period` asserting the actual fee, not `returns_correct_value`. Litmus test: if two reasonable implementations could both pass the suite yet behave differently for a user, it's under-specified — add the discriminating case until behavior is uniquely determined.

See `.claude/rules/testing.md` for file naming, directory layout, and per-area conventions.
```

## Rules

- Emit all thirteen rules. Do not drop one because it looks demanding — if the project can't hold a rule today, that is a gap to see, not a rule to soften.
- Rule 10 is the one exception worth annotating: if the project measures coverage today and is materially below 100%, append one sentence naming the current figure and that it is the direction of travel. Never lower the stated bar to match the status quo, and never invent a figure — if coverage isn't measured, say "Coverage is not measured yet."
- Every `{{...}}` must resolve to something discovered in this project. If a substitution has no real answer (no database, no coverage tool), rewrite the sentence to omit it rather than naming a service the project doesn't run.
- Do not duplicate `.claude/rules/testing.md`. Frameworks, file naming, and directory layout belong there; this file is policy only.
